## What Worked
- **The trade-layer trust boundary is airtight at the browser.** The client-facing SSR `/view/<token>` page and the JSON payload both carry only the reseller's brand + the sell price + the inherited gallery, and are structurally free of the licenseTerms string, the exact platform-take/seller-credit amounts, and every revenue-share/net-rate/markup/provenance/agencyId field. INV-020 holds on the real rendered document, not just the allowlist projection. The page tab title (`Kyoto balanced trip — Meridian Bespoke …`) carries the reseller brand and never leaks "TripForge".
- **Revenue share is conserved and correctly scoped.** The primary license created exactly one `marketplace_license` and one `revenue_share_ledger` row; the ledger row conserves (price = platform_take + seller_credit, INV-012); the seller sees `licenseCount=1` + `sellerCreditTotalMinor=29790` on their own card and **only** their own card. A second agency browsing the identical listing sees null earnings — the projection is per-viewer, not global.
- **Content carries through the trade.** An agent-upload gallery asset attached to the seller's itinerary is inherited **verbatim** by the reseller's white-label copy (same kind/url/alt), renders in the reseller's editable workspace copy (with a Remove control they own), and reaches the client's branded view with **no internal media-asset id** exposed.
- **Honest earnings copy.** The seller card explains "first-sale earnings above use the platform's fixed take rate, not this [declared 7.5%] share" — the UI does not pretend the declared resale share governs the first sale. This is a well-placed honesty affordance around the same area as the open `RESALE-SHARE-SEMANTICS` desk item.
- **The two-step draft/selectDraft flow, media register/attach, vetting gate, licensing, and the anonymous client view all worked on the first try** once the reseller was vetted (see BUG/friction note below).

## Friction Points
- **[FRICTION-1] The licensor must be a vetted agency, but `licenseListing` reports it only as a terminal `{status:"not_vetted"}` payload — there is no actionable "how to get vetted" affordance.** My first scenario run vetted only the seller; licensing returned `not_vetted` with no guidance. It's correct that a reseller must be vetted to acquire (trust gate), but from a new reseller's point of view the trade simply fails silently with an opaque status. A real reseller hitting this has no path forward in-product (vetting is an operator DB action, `agency_vetting`). Low severity for the loop (both sibling scenarios already vet the reseller), but a genuine product dead-end for the demand side.
- **[FRICTION-2] A url-source media asset with an unreachable URL renders a broken `<img>` on the client-facing branded view, with no placeholder/fallback.** My fixture used `https://images.example.test/…` (an agent-upload asset carrying an external URL); the browser logged one `ERR_NAME_NOT_RESOLVED` per client-facing page and the gallery `<img>` rendered broken. This is partly a test-fixture artifact — a real device upload is served via the in-app `/api/media/[id]` route (seed-0022a) and would resolve — but it exposes a real gap: the media library accepts a url-source asset without validating reachability, and the client-facing view (the agency's polished brand surface) shows a broken image rather than a graceful fallback. Only console error observed; not a crash.

## Bugs Found
None. This scenario **confirms** the trade-layer trust boundary rather than breaking it: all 52 L3 checks pass, revenue share conserves and scopes correctly, and the client surface leaks nothing. FRICTION-1/2 are UX/product-shape observations, not functional defects.

## Missing Features
(All within the operator-authorized P2 campaign scope; listed for triage. None is my scenario's cell — they are the *other* open coverage gaps this pass now sits beside.)
- **[FEAT-1] In-product agency vetting path (FRICTION-1).** A reseller that hits `not_vetted` has no self-serve or guided route to become vetted; vetting is an out-of-band operator insert. A "request verification" affordance (feeding the existing `agency_vetting` gate) would close the demand-side dead-end. Trust stays mechanical (Principle VI) — this is about *reachability* of the gate, not weakening it.
- **[FEAT-2] Media-URL reachability validation / client-view image fallback (FRICTION-2).** Either validate a url-source asset resolves at register time, or render a graceful placeholder on the client-facing view when an image 404s, so an agency's branded output never shows a broken photo.

## Improvements
- **[IMP-1] The seller earnings surface is a card sub-line, not a first-class view.** `licenseCount` + `sellerCreditTotalMinor` are projected onto the `/marketplace` listing card ("1 license · 297.90 USD earned"), which works, but there is still no dedicated seller-earnings/licenses page (the same gap pin `revenue-share-seller-visibility` recorded — the surface landed by enriching `browseListings`). A seller with many listings has no aggregate earnings view. Carry-over, not new.
- **[IMP-2] Consider surfacing the platform take-rate to the seller at list time**, not only after a sale — today the "fixed take rate, not this share" caveat appears next to earnings, but the listing form still asks for a "Revenue share %" that governs only future resales, which is easy to misread as the first-sale split (adjacent to `RESALE-SHARE-SEMANTICS`).
